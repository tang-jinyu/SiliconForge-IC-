# 面向数字 IC 竞赛流程的专用 Agent 实施方案

## 1. 我对这个想法的判断

我认为这个想法是成立的，而且方向是对的，但前提是你要把目标定义准确。

你真正要做的，不是“一个万能写 Verilog 的 AI”，而是“一个围绕数字 IC 竞赛全流程的研发协作系统”。这个定位非常重要，因为数字硬件和软件最大的差异，不在于代码语法，而在于约束、架构分解、验证闭环、资源时序、平台差异和工程可落地性。现在很多通用 AI 在 Verilog 上表现不稳定，本质上不是因为它不会写 always 块，而是因为它没有被强制放进真实硬件开发的工作流里。

所以你的想法有价值，而且有差异化。你的优势不在于再做一个聊天机器人，而在于把你已经验证过的一套比赛工作流固化成系统：

1. 解析赛题
2. 确定架构
3. 执行代码编写
4. 学习专区
5. 文档撰写

这五步非常适合作为产品主流程。它天然比“自由对话型多 agent”更容易做出效果，因为它是强流程、强输入、强输出的。

我对你的核心建议只有一句话：

先做“流程正确、约束正确、验证闭环正确”的 MVP，再做“多 agent 炫技”和“可爱粉色 UI”。

粉色页面和可爱交互完全可以做，而且会让产品更有个人风格，但它应该排在第 4 周，而不是第 1 周。

## 2. 一个月内的合理目标

一个月内，不要试图做成一个全能平台。合理目标应该是：

做出一个可演示的 MVP，能围绕一个具体赛题或一个具体模块，稳定跑通“题目解析 -> 架构方案 -> RTL 草案 -> 基本验证建议 -> 学习总结 -> 初版文档”这条链路。

更具体一点，一个月后的合格结果应该是：

1. 用户上传赛题 PDF、板卡资料、接口要求、约束说明。
2. Agent 能先把需求结构化，而不是直接开始写代码。
3. Agent 能根据模式切换输出不同风格的实现建议：FPGA、PSoC/SoC、ASIC。
4. Agent 生成的 RTL 不是纯行为级散写，而是按模块边界、时序路径、接口协议组织。
5. Agent 能提醒验证点、资源风险、时序风险、CDC/复位风险。
6. Agent 能自动生成“学习专区”和“文档初稿”。
7. 整个系统的输入输出有固定模板，可以持续迭代。

这里我默认你说的 PSoC 更接近“软硬协同的可编程 SoC 模式”。如果你说的是 Cypress PSoC 一类器件，后续只需要把该模式下的工具链和约束模板替换掉，不影响总体框架。

## 3. 正确的产品定义

### 3.1 产品定位

建议你把产品定义成：

“面向数字 IC 竞赛与训练场景的领域专用 Agent，核心能力不是自由聊天，而是基于流程、模式和验证约束，产出可执行的硬件研发结果。”

### 3.2 你的真正护城河

你的护城河不是大模型本身，而是下面这四件事：

1. 数字 IC 竞赛工作流模板化。
2. FPGA、PSoC/SoC、ASIC 三种模式的差异化约束模板。
3. RTL 生成前的架构分解和 RTL 生成后的验证闭环。
4. 论文、开源项目、比赛资料被整理成你的私有知识库，而不是临时问一句答一句。

### 3.3 第一版不要做成什么样

第一版不要做成下面这种形态：

1. 五个 agent 互相聊天，但没有固定输入输出。
2. 一上来就让模型直接写完整工程。
3. 不区分 FPGA、PSoC/SoC、ASIC。
4. 没有验证器，只靠你肉眼看代码。
5. 没有错误复盘和知识沉淀。

## 4. 推荐的系统框架

我建议你第一版采用“单主控 + 五个专家节点 + 模式路由 + 验证闭环”的结构，而不是开放式多 agent 群聊。

### 4.1 总体架构

系统可以分成 7 层：

1. 输入层
   负责接收赛题 PDF、板卡手册、接口协议、评分规则、约束条件、已有代码、参考论文和开源项目。
2. 解析层
   把自然语言和文档变成结构化需求，例如模块列表、输入输出、性能指标、资源约束、时钟复位策略。
3. 模式层
   根据 FPGA、PSoC/SoC、ASIC 选择不同的提示词模板、设计约束、验证重点和文档模板。
4. 专家层
   包含五个节点：赛题解析专家、架构专家、RTL 专家、学习专区专家、文档专家。
5. 工具层
   包含文档解析、知识检索、代码生成、仿真调用、日志记录、结果汇总。
6. 评估层
   对结果做结构完整性检查、规范检查、仿真检查、风险检查。
7. 交互层
   Web 页面或桌面页面。你的可爱粉色 UI 放在这一层，不影响核心能力开发。

### 4.2 五个核心节点的职责

#### A. 赛题解析节点

输入：赛题描述、评分标准、平台信息、交付要求。

输出：

1. 任务目标摘要。
2. 显式约束清单。
3. 隐含约束清单。
4. 待澄清问题列表。
5. 初步模块划分建议。

#### B. 架构节点

输入：结构化需求和模式信息。

输出：

1. 顶层模块图。
2. 时钟与复位策略。
3. 数据通路与控制通路划分。
4. 状态机、流水线、缓存、FIFO、仲裁等关键设计选择。
5. 风险点及替代架构。

#### C. RTL 节点

输入：架构方案、接口规范、编码风格约束。

输出：

1. 模块级 RTL 草案。
2. 接口定义。
3. 关键时序说明。
4. 必须验证的 corner case 列表。
5. 不确定点标注，而不是强行瞎写。

#### D. 学习专区节点

输入：当前赛题涉及的知识点、论文、开源项目。

输出：

1. 本题涉及的知识树。
2. 原理说明。
3. 易错点总结。
4. 推荐补学路径。
5. 对应到当前工程的理解映射。

#### E. 文档节点

输入：前四个节点的产物。

输出：

1. 项目摘要。
2. 系统框图。
3. 模块设计说明。
4. 仿真与验证说明。
5. 实验结果与后续优化方向。

### 4.3 三种模式的差异化重点

#### FPGA 模式

重点约束：板卡资源、时序收敛、厂商 IP、片上调试、吞吐与延迟折中。

Agent 需要重点关注：

1. DSP、BRAM、LUT、FF 资源消耗。
2. 时钟域划分与约束文件。
3. 上板可调试性。
4. 厂商原语和 IP 的使用边界。

#### PSoC/SoC 模式

重点约束：软硬件划分、寄存器接口、驱动、DMA、中断、带宽和系统联调。

Agent 需要重点关注：

1. 哪些功能放硬件，哪些放软件。
2. AXI/APB/自定义寄存器映射。
3. 驱动和固件接口文档。
4. 联调路径和性能瓶颈。

#### ASIC 模式

重点约束：可综合性、可测试性、Lint/CDC/复位规范、面积功耗时序、工艺无关表达。

Agent 需要重点关注：

1. 禁止依赖 FPGA 厂商特定原语。
2. 重视时钟门控、复位策略、CDC、DFT 预留。
3. 输出更规范的模块接口和设计说明。
4. 对面积、功耗、时序做更早期的风险提示。

## 5. 一个月实施计划

下面这版是我认为最稳的一个月推进方式。

### 第 1 周：收敛需求，先把输入输出定死

目标：不要先写 agent，对准“你的系统到底接什么、吐什么”。

本周任务：

1. 选一个具体赛题或一个具体功能模块做 MVP 场景。
2. 定义五个流程节点的标准输入输出格式。
3. 定义三种模式的差异化约束模板。
4. 建立知识库存储结构。
5. 先手工跑一遍流程，确认流程本身成立。

本周产物：

1. 需求模板。
2. 模式模板。
3. 节点输出模板。
4. 一份黄金样例。

### 第 2 周：实现“解析赛题 + 架构规划”

目标：让系统先学会正确理解题，不要急着生成 RTL。

本周任务：

1. 做文档解析和文本切分。
2. 做赛题结构化提取。
3. 做模式路由。
4. 做架构方案生成。
5. 让系统输出风险清单和待确认问题。

本周产物：

1. 题目解析器。
2. 架构规划器。
3. 三模式提示词模板初版。

### 第 3 周：实现“RTL 生成 + 验证建议 + 反思修正”

目标：开始写代码，但必须带验证和复盘。

本周任务：

1. 按模块生成 RTL，而不是一次性生成整个工程。
2. 加入自检提示，例如接口一致性、状态机完备性、复位逻辑、时序热点。
3. 接入至少一个基础仿真闭环。
4. 把错误信息重新喂回模型做一次修正。
5. 记录每次生成失败的原因。

本周产物：

1. RTL 生成节点。
2. 基础验证节点。
3. 反思修正节点。

### 第 4 周：补齐“学习专区 + 文档 + UI + 演示闭环”

目标：把系统从工程半成品变成可展示产品。

本周任务：

1. 根据当前赛题自动生成知识树和学习指南。
2. 自动汇总前面节点，输出文档初稿。
3. 做一个轻量但风格鲜明的 UI。
4. 跑通完整 demo。
5. 做一次人工评审，记录下一轮迭代点。

本周产物：

1. 学习专区节点。
2. 文档节点。
3. 演示视频或演示流程。
4. 下一阶段 backlog。

## 6. 技术实现建议

### 6.1 框架选型建议

如果目标是一个月内出结果，我建议：

1. 主工作流用 LangGraph 或你自己写的状态机，不建议一开始就做自由多 agent 对话系统。
2. 如果你想快速验证多 agent 协作，可以参考 AutoGen，但第一版不要让 agent 之间无限对话。
3. 知识库用最简单的文件系统加向量检索即可，不要一开始就做复杂平台。
4. 后端优先 Python，因为生态最成熟，和文档处理、Agent 框架、仿真脚本最好结合。

### 6.2 工程目录建议

建议你把工程组织成下面这种结构：

1. app: 后端入口和 API。
2. agents: 五个流程节点和模式路由。
3. prompts: 各节点模板。
4. knowledge: 论文、开源项目、赛题资料的结构化沉淀。
5. evaluators: 结果检查器和验证器。
6. examples: 样例赛题与标准输出。
7. ui: 前端页面。
8. logs: 每轮任务输入输出和失败原因。

### 6.3 最重要的工程原则

1. 结构化输入优先于华丽 prompt。
2. 模块级生成优先于整工程生成。
3. 验证闭环优先于一次生成成功。
4. 日志与复盘优先于不断换模型。
5. 先固定流程，再增加“智能度”。

## 7. 你应该给 AI 什么输入

这是最关键的一部分。你要喂给 AI 的不是“很多资料”，而是“被整理过的有效上下文”。

### 7.1 每次启动一个赛题时，至少给 AI 这些输入

1. 赛题原文。
2. 评分标准。
3. 目标平台信息。
4. 板卡或芯片手册。
5. 时钟、复位、接口、吞吐、延迟、面积、功耗等约束。
6. 允许使用和禁止使用的 IP/原语。
7. 你的编码风格要求。
8. 交付物要求，例如 RTL、testbench、报告、答辩 PPT。
9. 你已有的参考代码和历史项目。

### 7.2 你应该怎么组织这些输入

不要一股脑丢 PDF。建议整理成统一模板：

1. 任务目标。
2. 输入输出接口。
3. 平台模式。
4. 显式约束。
5. 隐含风险。
6. 已有参考。
7. 希望 AI 当前只做哪一步。
8. 当前不允许它做什么。

### 7.3 你最不该做的输入方式

1. “帮我把这个赛题做了。”
2. “直接写完整 Verilog。”
3. “你自由发挥选架构。”
4. “按你觉得好的方式实现。”

这些写法在软件上有时还能凑合，在硬件上风险很高。

## 8. 你应该优先喂给 AI 的论文和开源项目

下面我按优先级给你一个可执行清单。

### 8.1 第一优先级：Agent 方法论

1. ReAct: Synergizing Reasoning and Acting in Language Models
   你要让 AI 学到：先推理、再行动、再根据外部反馈更新计划。对你的系统最关键的启发是“不要只生成文本，要让模型驱动流程节点”。
2. Reflexion: Language Agents with Verbal Reinforcement Learning
   你要让 AI 学到：失败后要做语言级反思，把错误沉淀到下一轮，而不是每轮重新开始。
3. AutoGen 文档与示例
   你要让 AI 学到：多角色协作、工具调用、消息路由的工程组织方式。
4. LangGraph 文档与案例
   你要让 AI 学到：如何把 agent 系统做成可控状态机，而不是放任自由对话。
5. DSPy 文档与案例
   你要让 AI 学到：把 prompt 视作可优化程序，而不是一次性写死。

### 8.2 第二优先级：数字硬件工程与验证

1. cocotb
   你要让 AI 学到：如何用 Python 驱动硬件验证，如何把验证纳入 agent 工作流。
2. OpenTitan
   你要让 AI 学到：大型开源芯片项目如何组织文档、IP、验证、工具和规范。
3. LiteX
   你要让 AI 学到：FPGA/SoC 项目如何进行系统集成、模块组织和快速原型。
4. Verilator
   你要让 AI 学到：开源仿真和快速验证如何接入自动化流程。
5. Yosys
   你要让 AI 学到：综合视角下的可实现性检查思路。
6. Edalize
   你要让 AI 学到：如何把不同 EDA 工具链统一成可调用接口。
7. PyMTL3
   你要让 AI 学到：高层建模、Python 驱动硬件设计和测试的工程方式。

### 8.3 第三优先级：芯片领域专用大模型/评测方向

1. ChipNeMo: Domain-Adapted LLMs for Chip Design
   你要让 AI 学到：芯片领域确实需要领域适配，而不是纯通用模型硬套。
2. VerilogEval: Evaluating Large Language Models for Verilog Code Generation
   你要让 AI 学到：Verilog 生成不能只看语法，还要看功能正确性和评测方式。
3. 任何与 HDL 代码生成、硬件设计评测、EDA + LLM 结合相关的论文
   你要让 AI 学到：数字硬件任务的评价指标和失败模式与软件代码生成不同。

### 8.4 你的喂法不要是“全文投喂”

正确做法是：

1. 论文先自己读一遍，做 5 到 10 条笔记。
2. 把摘要、方法、你看懂的核心图、你的疑问一起给 AI。
3. 让 AI 输出“可迁移机制”，而不是泛泛总结。
4. 让 AI 说明这篇东西对应你五步流程中的哪一步。
5. 让 AI 给出“是否值得纳入系统”的结论。

## 9. 每看完一篇论文，应该怎么给 AI 写 prompt

你每次读完论文，不要只问“帮我总结”。正确问法是让 AI 做“论文到系统设计”的迁移。

下面给你一个通用模板。

### 9.1 论文消化 prompt 模板

你现在是我的数字 IC Agent 研发助手。下面是我刚看完的一篇论文的摘要、关键方法、我自己的理解和疑问。你的任务不是泛泛总结，而是把这篇论文转化成我可以放进系统里的方法组件。

请严格按下面结构输出：

1. 这篇论文试图解决什么问题。
2. 它的核心机制是什么，用尽量简单的话讲清楚。
3. 它依赖什么前提，在哪些情况下会失效。
4. 这篇论文里哪些机制可以迁移到我的数字 IC Agent。
5. 这些机制分别对应我的哪一个流程节点：赛题解析、架构、RTL、学习专区、文档。
6. 如果要在一个月内做 MVP，最值得实现的 1 到 2 个点是什么。
7. 给出可以直接落地的 prompt 模板、状态字段或工具接口建议。
8. 给出一份不建议照搬的内容清单，并说明原因。
9. 最后输出一份“纳入系统/暂不纳入系统”的结论。

我提供给你的材料如下：

1. 论文题目：
2. 摘要：
3. 核心方法：
4. 我理解的亮点：
5. 我的疑问：
6. 我的系统背景：面向数字 IC 竞赛，包含赛题解析、架构、RTL、学习专区、文档五个流程，并区分 FPGA、PSoC/SoC、ASIC 三种模式。

### 9.2 开源项目消化 prompt 模板

你现在是我的系统架构助手。下面是一个开源项目的 README、目录结构、核心模块和我的观察。请不要只做介绍，而要分析这个项目哪些设计值得吸收到我的数字 IC Agent 里。

请按下面结构输出：

1. 这个项目的定位和核心抽象。
2. 它的系统是如何组织模块、状态和工具的。
3. 它最值得学习的 3 个工程设计点。
4. 它不适合直接照搬到我项目里的部分。
5. 如果我只吸收 20% 最关键内容，应该吸收哪 20%。
6. 把可吸收内容映射到我的系统模块。
7. 给出我下一步可以实现的具体任务清单。

## 10. 让 AI 从论文/开源项目里“获得什么”

这是你后面会越做越强的关键。AI 不应该只是获得知识点，它应该获得下面 8 类资产：

1. 问题定义方式。
2. 输入输出结构。
3. 状态设计方式。
4. 工具调用方式。
5. 评估指标。
6. 常见失败模式。
7. 可以复用的 prompt 模板。
8. 可以沉淀成代码模块的工程模式。

你每看完一篇论文或一个项目，最好都沉淀下面这些文件：

1. 一页摘要。
2. 可迁移机制清单。
3. 不适用机制清单。
4. 可复用 prompt。
5. 可复用工具接口。
6. 对应到你系统 backlog 的新增事项。

## 11. 你自己应该具备哪些能力

这个项目能不能做起来，取决于你自己是否补齐三类能力。

### 11.1 数字 IC 核心能力

1. 同步时序设计基础。
2. FSM、流水线、FIFO、握手协议、仲裁、缓存等常见结构。
3. 可综合 RTL 写法和常见反模式。
4. 时钟、复位、CDC、亚稳态、时序路径等基础概念。
5. 资源与时序权衡。
6. testbench、波形分析、断言、覆盖率的基本方法。
7. FPGA、PSoC/SoC、ASIC 三种模式的工程差异。

### 11.2 Agent/LLM 工程能力

1. Prompt 设计与拆解。
2. 结构化输出设计。
3. 工具调用与工作流编排。
4. RAG 或知识检索的基本原理。
5. 日志、评估、错误复盘。
6. Python 工程能力。
7. 基本前后端联调能力。

### 11.3 产品化能力

1. 能定义 MVP，而不是一开始想做大全。
2. 能为每个节点定义可检查的输出。
3. 能建立评测样例。
4. 能从失败案例里提炼下一轮优化项。
5. 能把“你个人的工作流经验”转化成模板和规则。

## 12. 我建议你现在立刻做的事

如果今天就开始，我建议你按这个顺序启动：

1. 选一个你最熟悉的比赛题目或一个最典型模块做唯一 MVP 场景。
2. 手工写出五个流程节点的输入输出模板。
3. 先只支持 FPGA 模式，把它跑通。
4. 给每个节点写固定 prompt，而不是开放式问答。
5. 把 ReAct、Reflexion、AutoGen、cocotb、OpenTitan、LiteX 作为第一批资料。
6. 用 3 到 5 个真实失败案例建立你的评测集。
7. 第一个月结束前，完成一个可演示闭环，而不是追求三种模式全部完善。

## 13. 最后给你的总判断

这件事值得做，而且你是有机会做出特色的。

原因不是“你也会做 agent”，而是你比很多纯软件背景的人更清楚数字 IC 场景里什么叫真正有用：不是会说，而是能把题目拆对、架构定对、代码写得可综合、验证想得完整、文档收得下来。

如果你按上面的方式推进，一个月内完全有机会做出一个有说服力的第一版。关键不是模型多强，而是你能不能把你的专业工作流固化成一套结构化系统。

如果后续继续迭代，你的路线应该是：

先把流程做深，再把模式做宽；先把验证做强，再把界面做美；先把一个场景做透，再扩到更多比赛和更多芯片类型。
